## wxWidgets 线程模型与最佳实践

### 1. 整体线程模型

- `wxUSE_THREADS=1` 时，wxWidgets 提供完整的线程与同步封装（见 `include/wx/thread.h`、`include/wx/msgqueue.h`）。
- 推荐模型是：**单 GUI 线程 + 多个工作线程**。
  - GUI 线程：创建 `wxApp`、窗口和事件循环的主线程（`wxThread::IsMain()` 返回 `true`，`wxThread::GetMainId()` 标识它）。
  - 工作线程：执行耗时或阻塞任务，不直接访问 GUI。
- 新代码中，官方建议**优先使用 C++11 及以后的并发库**（`std::thread/std::mutex/std::condition_variable` 等），仅在需要与 wxWidgets 深度集成时使用 `wxThread` 系列类。

### 2. 禁止在工作线程直接操作 GUI

文档与实现中明确强调：

- **非 GUI 线程不得调用任何 GUI 相关 API**（创建/销毁窗口、修改控件、绘图等）。
- 正确做法：
  - 在工作线程中计算/准备数据；
  - 通过线程安全的事件或队列把结果投递回主线程；
  - 在主线程事件处理函数中真正更新界面。

常用的 GUI 线程通信方式：

- `wxEvtHandler::QueueEvent()` / `::wxQueueEvent()`：线程安全地向任意 `wxEvtHandler` 投递事件。
- `wxEvtHandler::CallAfter()`：在 GUI 线程上排队执行一个回调（内部仍通过事件机制）。
- `wxThreadEvent`：专门用于线程间通知，事件类别为 `wxEVT_CATEGORY_THREAD`，不会被 `wxEventLoopBase::YieldFor()` 意外处理。

历史上存在 `wxMutexGuiEnter()/wxMutexGuiLeave()`（以及 `wxMutexGuiLocker`），允许在持有 GUI 锁的前提下在非 GUI 线程调用少量 GUI 操作，但官方注释已经明确**不再推荐在新代码中使用**，且在不同平台存在安全性问题，应视为兼容遗留方案。

### 3. 线程与同步相关核心类

基于 `include/wx/thread.h` 与 `include/wx/msgqueue.h`，wxWidgets 的线程工具主要包括：

#### 3.1 wxThread：线程封装

- 创建线程：
  - 继承 `wxThread`，重写 `virtual void* Entry() override` 作为线程入口。
  - 构造时指定线程类型：`wxTHREAD_DETACHED` 或 `wxTHREAD_JOINABLE`。
  - 调用 `Create()` 创建系统线程，再调用 `Run()` 启动。
- 线程类型：
  - `wxTHREAD_DETACHED`（默认）：
    - 线程结束后自动销毁自身对象；
    - 不能通过 `Wait()` 获取返回值；
    - 通常用于“火并忘（fire-and-forget）”类型任务。
  - `wxTHREAD_JOINABLE`：
    - 用户代码负责在适当时机调用 `Wait()` / 删除线程对象；
    - 可以通过 `Wait()` 获取 `ExitCode`；
    - 更安全，适合需要明确生命周期管理的任务。
- 生命周期控制：
  - `Create()`：创建底层线程对象。
  - `Run()`：启动执行 `Entry()`。
  - `Delete(ExitCode* rc = nullptr, wxThreadWait waitMode = wxTHREAD_WAIT_DEFAULT)`：
    - 发送终止请求，等待线程在内部调用 `TestDestroy()` 后退出；
    - 对于 joinable 线程，不会自动删除线程对象，仍需外部删除。
  - `Wait()`：等待 joinable 线程结束，返回 `ExitCode`。
  - `Kill()`：**强制杀死线程，不进行清理，不推荐在正常路径中使用**。
  - `Pause()/Resume()`：挂起/恢复线程执行，要求线程经常调用 `TestDestroy()`。
- 线程内部需定期调用：
  - `bool TestDestroy()`：检测是否被请求终止，返回 `true` 时应尽快清理后退出 `Entry()`。
- 回调钩子：
  - `virtual void OnExit()`：在线程自然退出时，在该线程上下文中调用。
  - `virtual void OnDelete()`：`Delete()` 触发，在调用 `Delete()` 的线程中执行。
  - `virtual void OnKill()`：`Kill()` 触发，在调用 `Kill()` 的线程中执行。

辅助工具：

- `wxThreadHelper` / `wxThreadHelperThread`：
  - 简化“某个类拥有一个线程”的场景；
  - 把线程对象与拥有者对象绑定，隐藏部分样板代码。

#### 3.2 同步原语

- `wxMutex`：
  - 提供互斥锁，支持 `Lock()/TryLock()/LockTimeout()/Unlock()`；
  - `wxMutexLocker`：RAII 封装，构造时加锁，析构时解锁，避免遗忘。
  - `wxMutexType`：
    - `wxMUTEX_DEFAULT`：普通互斥锁（推荐默认使用）。
    - `wxMUTEX_RECURSIVE`：递归互斥锁，**不应与 `wxCondition` 一起使用**，在某些 Unix 平台会导致死锁。
- `wxCriticalSection`：
  - 进程内的轻量级互斥，部分平台直接用 `wxMutex` 实现；
  - 通常适用于保护小范围的共享状态（比如全局数组）。
  - `wxCriticalSectionLocker`：RAII 封装。
- `wxCondition`：
  - 条件变量，配合一个 `wxMutex` 使用；
  - 支持 `Wait()` / `WaitTimeout()` / `Signal()` / `Broadcast()`；
  - 典型用途：等待队列有数据、等待状态改变。
- `wxSemaphore`：
  - 计数信号量，实现对资源访问数量的限制；
  - `Wait()` / `TryWait()` / `WaitTimeout()` / `Post()`。

#### 3.3 wxMessageQueue<T>：线程间消息队列

定义于 `include/wx/msgqueue.h`，典型场景为主线程与工作线程之间的命令/结果队列。

- 特点：
  - 模板类，可传递任意类型的消息（值或 move-only 对象）。
  - 内部使用 `wxMutex` + `wxCondition` 实现，接口简单。
- 关键接口：
  - `Post(const Message& msg)` / `Post(Message&& msg)`：从任意线程安全地推入消息。
  - `Receive(T& msg)`：在队列为空时阻塞等待，直到有消息。
  - `ReceiveTimeout(long timeout, T& msg)`：等待指定时间，超时返回 `wxMSGQUEUE_TIMEOUT`。
  - `Clear()`：清空队列，一般在发送端取消任务时调用。
- 典型用法：
  - 主线程 `Post()` 控制消息（开始、停止、更新参数）；
  - 工作线程在 `Entry()` 中循环 `Receive()`，根据消息执行不同操作；
  - 停止线程时发送专门的“退出消息”而不是粗暴杀死线程。

#### 3.4 线程相关宏

- `wxCRITICAL_SECTION(name)`：
  - 在 `wxUSE_THREADS=1` 时展开为静态 `wxCriticalSection` + 自动锁；
  - 在禁用线程的构建中零开销；
  - 适合用来保护静态/全局计数器等，同时兼顾单线程/多线程配置。

### 4. 推荐的线程设计模式

结合 `docs/doxygen/overviews/thread.h` 与 `samples/thread/thread.cpp`，在 wxWidgets 中使用线程时推荐采用以下模式。

#### 4.1 单 GUI 线程 + 多工作线程

- 所有窗口和 GUI 事件处理都在主线程；
- 工作线程只做计算、IO、阻塞操作，通过事件或队列向主线程报告结果；
- 工作线程任何需要更新界面的动作都封装为：
  - 向某个窗口 `QueueEvent()` / `CallAfter()`；
  - 或向主线程拥有的 `wxMessageQueue` 发送消息，再在主线程轮询/等待处理。

#### 4.2 使用 joinable 线程安全结束任务

最佳实践：

- 默认使用 **joinable 线程**（`wxTHREAD_JOINABLE`），显式管理其生命周期；
- 启动线程：

```cpp
class MyWorkerThread : public wxThread
{
public:
    MyWorkerThread(wxEvtHandler* handler)
        : wxThread(wxTHREAD_JOINABLE), m_handler(handler) {}

    virtual ExitCode Entry() override
    {
        while ( !TestDestroy() )
        {
            // 执行耗时任务…

            // 把结果投递到 GUI 线程
            wxThreadEvent* evt = new wxThreadEvent(wxEVT_THREAD, WORKER_EVENT);
            evt->SetInt(42);
            wxQueueEvent(m_handler, evt);
        }
        return nullptr;
    }

private:
    wxEvtHandler* m_handler;
};
```

- 主线程管理生命周期：
  - 持有 `MyWorkerThread*` 指针；
  - 在关闭窗口或需要停止时调用 `Delete()` 请求线程退出；
  - 再调用 `Wait()` 等待结束，并在适当位置删除线程对象。

#### 4.3 使用 wxThreadEvent / CallAfter 更新 GUI

两种常见方式：

1. 事件方式：
   - 工作线程构造 `wxThreadEvent`，设置数据，使用 `wxQueueEvent()` 投递；
   - 主线程在 `EVT_THREAD` 处理函数中读取数据并更新界面。
2. `CallAfter` 方式：
   - 工作线程调用 `wxTheApp->CallAfter([=]{ /* 更新 GUI */ });`；
   - 逻辑直接在 GUI 线程执行，避免显式定义事件类型。

两者都遵守“工作线程不直接操作控件”的原则。

#### 4.4 使用 wxMessageQueue<T> 实现命令驱动的工作线程

简化版模式如下：

```cpp
enum class WorkerCmd { DoWork, Quit };

wxMessageQueue<WorkerCmd> g_cmdQueue;

class QueueWorker : public wxThread
{
public:
    QueueWorker() : wxThread(wxTHREAD_JOINABLE) {}

    virtual ExitCode Entry() override
    {
        for (;;)
        {
            WorkerCmd cmd;
            if ( g_cmdQueue.Receive(cmd) != wxMSGQUEUE_NO_ERROR )
                break;

            if ( cmd == WorkerCmd::Quit )
                break;

            // 执行对应任务…
        }
        return nullptr;
    }
};
```

- 主线程根据用户操作向队列发送不同 `WorkerCmd`；
- 退出时发送 `Quit`，而不是调用 `Kill()`。

### 5. 反模式与注意事项

为避免在 wxWidgets 中引入微妙的多线程 bug，建议遵守以下约束：

- 不要在非主线程直接创建或操作任何 `wxWindow` / `wxDC` 等 GUI 对象。
- 避免滥用 `wxThread::Kill()`，除非在无法正常终止的极端场景。
- 对 joinable 线程必须在某处调用 `Wait()` 并负责销毁对象，避免泄漏。
- 使用 `wxCondition` 时避免搭配递归互斥锁（`wxMUTEX_RECURSIVE`），否则在部分 Unix 平台会死锁。
- 线程内长时间循环/阻塞时务必定期调用 `TestDestroy()`，否则 `Delete()`/`Pause()` 等控制操作会失效。
- 使用 `wxEventLoopBase::YieldFor()`（或间接通过 `wxProgressDialog`）时，留意事件处理顺序可能改变；对于线程事件，优先使用 `wxThreadEvent`，其事件类别可避免被 `YieldFor()` 非预期处理。

### 6. 新代码的推荐实现方向

综合 wxWidgets 源码与文档中的建议，在新项目或重构代码时可以采用：

1. **业务逻辑并发层**：使用 C++ 标准库并发原语（`std::thread`/`std::mutex`/`std::condition_variable`/`std::future` 等）。
2. **与 GUI 的桥接层**：仅在需要与 wxWidgets 事件系统交互时使用：
   - `wxEvtHandler::CallAfter()` / `wxQueueEvent()` / `wxThreadEvent` 把结果和状态回传给 GUI；
   - 如需队列式命令处理，可选择 `wxMessageQueue<T>` 或自己封装的队列。
3. **严格遵守“GUI 只在主线程访问”这一核心原则**，把所有 UI 更新集中在事件处理函数中完成。

以上模型与 wxWidgets 自带的线程文档（`docs/doxygen/overviews/thread.h`）和示例（`samples/thread/thread.cpp`）保持一致，可作为本项目中多线程设计与实现的总体指南。

### 7. wxImageRenderer 项目内实现约定

本项目（`player` 子目录内的 wxImageRenderer）在整体上遵循前述 wxWidgets 线程模型，同时结合自身架构做了更细化的约定。

#### 7.1 线程角色划分

- **UI 线程（主线程）**
  - 由 `wxir::ui::MainApp`（`src/ui/MainApp.h`）创建和管理，是唯一运行 wxWidgets 事件循环的线程。
  - 所有 `wxWindow` / `wxFrame` / `wxTimer` 等 GUI 对象均在此线程创建和销毁。
  - 所有 UI 更新（菜单、控制条、状态栏、对话框等）必须在此线程执行。

- **渲染线程**
  - 由 `wxir::ui::MainFrame` 内的 `std::thread renderThread_` 启动，入口函数为 `RenderThreadMain()`（`src/ui/MainFrame.h`）。
  - 负责驱动 `IRenderer`、`IImageSource` 等核心渲染逻辑以及图像帧处理。
  - 严格禁止在渲染线程内直接调用任何 wxWidgets GUI API；渲染线程只操作核心层 C++ 对象（`IRenderer`、`ImageFrame` 等）。

- **未来扩展线程**
  - 若后续引入解码线程、预处理线程等，必须同样遵守：
    - 不直接操作 GUI；
    - 通过队列/消息进行通信；
    - 采用统一的关闭与错误传播机制（见下文）。

#### 7.2 线程间通信约定：ThreadMessenger

项目使用 `wxir::ThreadMessenger`（`src/core/thread/ThreadMessenger.h`）作为**唯一的线程通信管理器**，协调 UI 线程与渲染线程：

- **所有跨线程控制命令和状态通知都通过 ThreadMessenger 完成**，避免模块各自定义零散的消息通道。
- `MainApp` 持有全局唯一的 `std::unique_ptr<ThreadMessenger>`：
  - 通过 `MainApp::GetThreadMessenger()` 暴露给 UI 层和核心层使用；
  - 其它模块不得自行创建额外的 `ThreadMessenger` 实例。

消息模型：

- 消息类型由 `enum class MessageType` 定义，当前包括：
  - `Play` / `Pause` / `Stop` / `Seek`：播放控制；
  - `Resize`：窗口或渲染区域尺寸变化（对应 `ResizeMessage`）；
  - `ScaleModeChanged`：缩放模式变更（对应 `ScaleModeMessage`）；
  - `FrameReady`：新渲染帧就绪（对应 `FrameMessage`，携带 `ImageFrame`）；
  - `Error`：渲染/解码错误通知；
  - `Shutdown`：请求目标线程优雅退出。

- 基础消息结构 `Message`：
  - 包含 `MessageType type`、时间戳 `timestamp` 和泛型 `data`（`std::shared_ptr<void>`）；
  - 通过模板构造函数和 `GetData<T>()/GetSharedData<T>()` 实现类型安全的访问；
  - 要求：实际使用时必须明确约定每个 `MessageType` 对应的 `T` 类型，避免类型不匹配。

通信方向与约定：

- **UI → 渲染线程**
  - 使用 `PostToRenderThread(Message&& message)` 或宏 `WXIR_POST_TO_RENDER(messenger, type, ...)`。
  - 典型场景：
    - 用户操作触发播放控制（播放/暂停/停止/Seek）；
    - 窗口大小变化时发送 `ResizeMessage` 通知渲染线程调整视口；
    - 缩放模式菜单/按钮修改后发送 `ScaleModeMessage`。

- **渲染线程 → UI**
  - 使用 `PostToUIThread(Message&& message)` 或宏 `WXIR_POST_TO_UI(messenger, type, ...)`。
  - 典型场景：
    - 新帧准备好，发送 `FrameReady`，UI 线程在 `OnFrameReceived()` 内调用 `RenderFrame()` 然后触发重绘；
    - 渲染或资源错误发送 `Error`，UI 线程负责弹窗、状态栏提示或切换降级模式。

消息处理方式：

- `ThreadMessenger` 内部为两个方向分别维护 `ThreadSafeQueue<Message>`：
  - `renderThreadQueue_`：UI 线程入队，渲染线程出队；
  - `uiThreadQueue_`：渲染线程入队，UI 线程出队。
- 通过 `ProcessRenderThreadMessage()` / `ProcessUIThreadMessage()` 拉取消息并根据注册的 `MessageHandler` 分发：
  - 渲染线程在主循环中周期性调用 `ProcessRenderThreadMessage()`；
  - UI 线程在 `MainFrame::HandleRenderMessages()` 中处理来自渲染线程的消息；该函数应在 `OnIdle`、`wxTimer` 或相关 UI 事件中定期调用。
- 消息处理器通过：
  - `RegisterRenderThreadHandler(MessageType, MessageHandler)`；
  - `RegisterUIThreadHandler(MessageType, MessageHandler)`；
  注册时需持有 `handlersMutex_`，并建议在启动任何线程之前完成注册，以避免竞争条件。

#### 7.3 ThreadSafeQueue 使用与关闭协议

项目自定义的 `ThreadSafeQueue<T>`（`src/core/thread/ThreadSafeQueue.h`）是所有线程间队列的基础：

- 基本操作：
  - `Push()`/`TryPush()`：线程安全入队；
  - `Pop()`/`Pop(timeout)`：阻塞或限时出队（支持关闭检测）；
  - `TryPop()`：非阻塞尝试出队。
- 关闭协议：
  - 调用 `Shutdown()` 将 `shutdown_` 置位并 `notify_all()`，使所有阻塞在 `Pop()` 的线程尽快返回；
  - 线程循环中收到 `Pop()` 返回 `false` 或检测到 `IsShutdown()` 时必须尽快退出主循环，执行清理逻辑。

与应用生命周期的关系：

- `MainApp::OnExit()` 中调用：
  - `mainFrame_->ShutdownRenderer()`：请求渲染线程退出并 `join()`；
  - `threadMessenger_->Shutdown()`：关闭所有队列，确保无残留阻塞。
- 约定：
  - 任何线程在退出前必须停止向队列 `Push()` 新消息；
  - 不允许在 `Shutdown()` 调用之后再访问 `ThreadMessenger` 或 `ThreadSafeQueue`，避免使用已关闭资源。

#### 7.4 项目内创建新线程的规则

为保持线程模型简单可控，本项目对新增线程提出以下约定：

1. **统一入口与命名**
   - 每个线程必须有清晰的入口函数（如 `XXXThreadMain()`），并在对应类中集中声明；
   - 线程对象命名统一为 `xxxThread_`，运行状态使用 `std::atomic<bool> xxxThreadRunning_{false};` 管理。

2. **禁止直接操作 GUI**
   - 所有新线程均不得直接访问任何 wxWidgets GUI 对象；
   - 需要更新 UI 时必须通过：
     - `ThreadMessenger` + `MainFrame::HandleRenderMessages()`；
     - 或 UI 线程侧的 `CallAfter()/QueueEvent()` 的桥接封装。

3. **通信统一走消息/队列**
   - 线程间共享数据优先使用 `ThreadSafeQueue<T>` + 明确的消息结构，而不是共享可变对象；
   - 必要时可以在特定模块内再封装轻量级队列，但不得绕过既有的 `ThreadMessenger` 与消息类型约定。

4. **优雅退出**
   - 每个线程必须支持通过消息或原子标志优雅退出（例如处理 `MessageType::Shutdown` 或检查 `running` 标志）；
   - 禁止在项目代码中使用类似 `std::terminate()` 或强行终止线程的方式结束线程。

#### 7.5 与 wxWidgets 线程模型的对齐

综合而言，wxImageRenderer 项目的线程设计在实现上：

- 使用 C++17 标准库并发原语（`std::thread`/`std::mutex`/`std::condition_variable`/`std::atomic`）实现业务层并发；
- 使用 `ThreadMessenger` + `ThreadSafeQueue` 实现强类型、可扩展的跨线程消息通信；
- 严格遵守 wxWidgets 对 GUI 访问的要求，将所有 UI 操作集中在主线程；
- 通过清晰的生命周期与关闭协议，避免阻塞退出和资源泄漏问题。

这些约定应作为本项目后续开发与代码评审时的统一参考标准。
